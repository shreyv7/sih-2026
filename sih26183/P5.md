# SIH26183 — ROLE 5 RESEARCH REPORT
## Data Sources, APIs & Technical Ingestion Architecture
### Problem Statement: Real-Time Identification of Fraud-Linked Cryptocurrency Exchanges from Victim-Reported Suspect Wallet Addresses through Automated Blockchain Analytics
**Domain:** Blockchain & Cybersecurity | **Target Ministry:** Ministry of Home Affairs (MHA) / Indian Cyber Crime Coordination Centre (I4C) | **Category:** Software

---

## 1. Executive Summary & Ingestion Strategy

- **The Multi-Chain Fragmentation Dilemma:** No single free-tier API provider delivers comprehensive, deep historical transaction indexing across **EVM chains (Ethereum, Polygon, BNB Chain)**, **TRON (TRC-20)**, and **Bitcoin (UTXO)**. A viable SIH prototype requires a coordinated multi-provider ingestion layer utilizing specialized adapters per blockchain family.
- **The Primary Target Stack (EVM + TRON):** Over 90% of retail cyber fraud in India (task scams, Ponzi investment schemes, fake trading apps) moves through **USDT on TRON (TRC-20)** and **EVM chains**. Ingestion must prioritize:
  1. **TronGrid API:** The only dedicated provider exposing pre-indexed account-level TRC-20 transfer histories without requiring local full-node transaction parsing.
  2. **Alchemy & Etherscan / Blockscout:** Alchemy provides the most generous permanent free EVM tier (30M Compute Units/month, no credit card required), while Etherscan and Blockscout provide indexed account-level transaction endpoints (`tokentx`, `txlistinternal`).
- **Etherscan Free-Tier Policy Shifts:** Etherscan tightened its free API terms: maximum records returned per paginated call was reduced from 10,000 to 1,000, and bulk internal transactions by block range were deprecated. Ingestion workers must incorporate automated pagination handlers to navigate this boundary.
- **API Ingestion vs. Self-Hosted Archive Nodes:** Operating a private Ethereum archive node requires over 12 TB of high-performance NVMe storage, 64 GB RAM, continuous high-bandwidth connectivity, and weeks of initial state synchronization. For a hackathon prototype, self-hosting is an unnecessary operational risk; developer APIs wrapped in an aggressive caching layer provide superior reliability and performance.
- **Defining "Real-Time" for Frontline Triage:** For an investigative prototype handling victim complaints, "real-time" denotes **on-demand reactive ingestion within $\le 5$ seconds** of case opening, rather than continuous full-ledger streaming. Push-based webhooks (Alchemy Notify / QuickNode Streams) are identified as future production extensions.
- **The Mandatory Caching Layer:** Free developer APIs enforce strict rate ceilings (e.g., TronGrid's 15 requests/sec with a 30-second lockout penalty, Etherscan's 5 calls/sec). A two-tier local cache (In-Memory LRU + SQLite/Redis) is essential to prevent rate exhaustion during multi-hop graph expansion and live presentations.

### Core Terminology
- **Compute Units (CU) / Credits:** A dynamic pricing model used by providers like Alchemy and Infura. Instead of charging a flat request fee, queries are weighted by computational complexity. For example, a basic `eth_blockNumber` costs 10 CUs, whereas a heavy `eth_getLogs` filter scanning 2,000 blocks costs 75 CUs.
- **Rate Limit & Throttling:** The maximum request velocity permitted per second (RPS) or per day. Violations trigger HTTP `429 Too Many Requests` or temporary IP bans.
- **Full Node vs. Archive Node:** A Full Node stores recent blockchain state and prunes historical contract storage snapshots; an Archive Node preserves the entire historical state trie since genesis. Ingesting historical token balances from 6 months ago requires archive state access or an explorer's indexed database.
- **Account Model vs. UTXO Ingestion:** Account-based chains (Ethereum, TRON) track global account balances; token movements are emitted via contract event logs (`Transfer`). Bitcoin tracks discrete unspent outputs (UTXOs); reconstructing a wallet's balance requires querying all unspent outputs and change transactions across historical blocks.

│                                                                                                        │
│   [Ingestion Request: Query Address 0x9B41...]                                                         │
│                          │                                                                             │
│                          ▼                                                                             │
│   [Tier 1: Local Cache Lookup] ──(Hit: <5ms)──► Return Cached JSON (Zero External Network Overhead)   │
│                          │                                                                             │
│                   (Miss: Not in Cache)                                                                 │
│                          │                                                                             │
│                          ▼                                                                             │
│   [Tier 2: Sliding-Window Token Bucket Limiter]                                                        │
│   - Enforces strict ceiling: TronGrid $\le 12 \text{ req/sec}$ (below 15 limit)                        │
│   - Enforces strict ceiling: Etherscan $\le 4 \text{ req/sec}$ (below 5 limit)                         │
│                          │                                                                             │
│                          ▼                                                                             │
│   [Tier 3: Exponential Backoff with Jitter]                                                            │
│   If HTTP 429 encountered:                                                                             │
│   $T_{\text{wait}} = \min\left(T_{\max}, \; T_{\text{base}} \cdot 2^{\text{attempt}}\right) + \text{rand}(0, 1)$│

## 9. Strategic Evaluator Q&A & Defensibility Guide

### Q1: Why not build your own blockchain indexer instead of relying on external APIs?
**Answer:** Building a custom multi-chain indexer requires running dedicated archive nodes, writing custom event listeners, and managing PostgreSQL transaction tables across gigabytes of block data. For a prototype, that diverts engineering effort away from our primary challenge: **identifying fraud-linked exchanges and automating police freeze notices**. Using developer APIs provides production-grade data immediately, while our local caching layer guarantees complete operational resilience.

### Q2: What happens if TronGrid rate-limits or locks out your API key during a live presentation?
**Answer:** We implement a **Double-Layered Defense**:
1. *Pre-Loaded Investigation Cache:* During live evaluation demos, all test cases are pre-cached in our local SQLite store. Queries resolve locally in $< 5 \text{ milliseconds}$ without generating external network traffic.
2. *Sliding Token-Bucket Throttling:* For live unseen address lookups, our dispatcher caps outbound requests at 10 req/sec (safely below TronGrid's 15 req/sec threshold), eliminating lockout risks entirely.

### Q3: How do you capture stablecoin transactions if Etherscan only shows native ETH?
**Answer:** Native RPC methods (`eth_getTransactionByHash`) only return native ETH transfers. We explicitly query Etherscan's `tokentx` endpoint and TronGrid's `/v1/accounts/{address}/transactions/trc20` endpoint. These APIs parse smart contract event topics (`Transfer(address,address,uint256)`), allowing our system to accurately ingest USDT movements.

### Q4: What does "real-time" mean in your proposed system?
**Answer:** In the context of the National Cyber Crime Reporting Portal (NCRP), a victim files a complaint 30 to 120 minutes after an incident. "Real-time" does not require listening to unconfirmed mempool transactions; it means **autonomous end-to-end multi-hop traversal and CEX identification in under 10 seconds** from the moment an officer enters the suspect address, replacing 90 minutes of manual block explorer navigation.
