# SIH26183 — ROLE 2 RESEARCH REPORT
## Blockchain Analytics & Transaction Tracing
### Problem Statement: Real-Time Identification of Fraud-Linked Cryptocurrency Exchanges from Victim-Reported Suspect Wallet Addresses through Automated Blockchain Analytics
**Domain:** Blockchain & Cybersecurity | **Target Ministry:** Ministry of Home Affairs (MHA) / Indian Cyber Crime Coordination Centre (I4C) | **Category:** Software

---

## 1. Executive Summary

- **Primary Objective:** Given a victim-reported suspect wallet address, mathematically reconstruct its transaction history, model the movement of funds as a Directed Graph, and follow fund flows forward (to cash-out points) and backward (to source deposits) across multi-hop paths.
- **Core Tracing Workflow:** 
  $$\text{Victim Ingestion} \longrightarrow \text{API Data Acquisition} \longrightarrow \text{Transaction Normalization} \longrightarrow \text{DAG Construction} \longrightarrow \text{Pruned Traversal} \longrightarrow \text{Trace Serialization}$$
- **The Token-Transfer Reality:** Over 90% of Indian retail cyber fraud complaints (task scams, illegal betting apps, fake investment portals) involve **USDT on TRON (TRC-20)** and **EVM chains (Ethereum, Polygon, BNB Chain)**. Tracing cannot rely on native asset transactions alone; it must ingest smart contract `Transfer` events (`tokentx` / TRC-20 endpoints) and internal contract calls (`txlistinternal`).
- **Graph Pruning & Noise Suppression:** Unrestricted multi-hop crawling triggers an exponential state-space explosion (high fan-out addresses can spawn thousands of edges). Algorithmic forward tracing must enforce deterministic constraints: bounded search depth ($k \le 4$ hops), incident-time window filtering ($t \ge t_{\text{incident}}$), and value-taint thresholds ($\ge \tau$) to filter out dusting spam and irrelevant micro-transactions.
- **Taint-Tracking Methodology:** To handle transaction splits and co-mingled balances accurately, the system formalizes an explainable **Proportional Haircut / Taint Model**, tracking the fraction of illicit value flowing through intermediary burner wallets down to custodial exchange deposit addresses.
- **Role Boundary & Integration:** Role 2 does not assign final legal culpability or make speculative ownership claims. It provides a deterministic, mathematically verifiable, and court-admissible **Forensic Transaction Trail** that feeds directly into Role 3 (Exchange Attribution) and Role 4 (Fraud Pattern Detection).

## 2. Technical Foundations & Core Terminology

| Concept / Term | Technical Definition | Operational Relevance to SIH26183 |
| :--- | :--- | :--- |
| **Address / Account** | A 20-byte (EVM: `0x...`) or 21-byte (TRON: `41...` / Base58Check: `T...`) public key hash representing an entity state on-chain. | The starting root vertex $V_0$ in the investigation graph. Contains zero native PII. |
| **Transaction Hash (`tx_hash`)** | A 32-byte cryptographic SHA-256 or Keccak-256 digest identifying a discrete block state transition. | Unique, immutable evidentiary anchor submitted in statutory legal requisitions. |
| **ERC-20 / TRC-20 Token Transfer** | A smart contract state mutation logged via event topic `Transfer(address indexed from, address indexed to, uint256 value)`. | **Crucial:** Scammers move stablecoins (USDT/USDC). Native RPC methods do not return these; event logs must be decoded. |
| **Internal Transaction** | A value transfer initiated by contract execution logic (`CALL`, `DELEGATECALL`) rather than an externally owned account (EOA). | Essential for tracing interactions through DEX aggregators, multi-sig vaults, and smart contract sweepers. |
| **Directed Weighted Graph $G(V, E)$** | Graph structure where vertices $V$ represent addresses and directed edges $E = (u, v)$ represent transactions from $u$ to $v$. | The core mathematical abstraction for link analysis, traversal algorithms, and forensic visualization. |
| **Edge Attributes** | Metadata mapped to each edge: amount $w(e)$, asset symbol $a$, timestamp $t$, block height $b$, and transaction hash $h$. | Preserves the forensic chain of custody required for Section 63 BSA / Section 65B IEA evidence admissibility. |
| **Forward Tracing** | Breadth-First traversal following outgoing directed edges ($u \to v$) starting from the suspect address ($V_0$). | Identifies the downstream layering path leading to the cash-out centralized exchange (CEX). |
| **Backward Tracing** | Reverse traversal following incoming edges ($u \leftarrow v$) into the suspect address ($V_0$). | Uncovers preceding funding sources, victim collection consolidation, or gas-funding parent wallets. |
| **Multi-Hop Depth ($k$)** | The geodesic distance (number of edges) traversed from the root node: $V_0 \xrightarrow{1} V_1 \xrightarrow{2} V_2 \dots \xrightarrow{k} V_k$. | Constrained to $k \le 4$ based on empirical cyber fraud laundering typologies in India. |

## 3. Comparative Blockchain Execution Models: Account vs. UTXO

Tracing logic is strictly dictated by the underlying blockchain accounting architecture. Applying account-based assumptions to UTXO ledgers—or vice versa—produces completely invalid forensic trails.

```
                  ACCOUNT-BASED MODEL (EVM / TRON)                     UTXO MODEL (BITCOIN)
           ┌──────────────────────────────────────────────┐     ┌──────────────────────────────────┐
           │ • Global State Trie / Account Balances       │     │ • Graph of Unspent Tx Outputs    │
           │ • Single Sender (from) ──► Recipient (to)    │     │ • Multiple Inputs ──► Multi-Outs │
           │ • Token transfers emitted via Event Logs     │     │ • Change address generated       │
           │ • Primary Indian fraud vehicle (USDT TRC-20) │     │ • Common-Input-Ownership (CIOH)  │
           └──────────────────────────────────────────────┘     └──────────────────────────────────┘
```

### In-Depth Architectural Comparison

| Architectural Aspect | Account-Based Model (Ethereum, Polygon, TRON) | UTXO Model (Bitcoin, Litecoin) |
| :--- | :--- | :--- |
| **State Storage** | Global state tree mapping `Address` $\to$ `(Nonce, Balance, StorageRoot, CodeHash)`. | Set of all Unspent Transaction Outputs (`UTXO Set`) stored in an indexed database (LevelDB). |
| **Transaction Structure** | Single sender (`from`), single recipient (`to`), value, gas price, nonce, and optional execution data payload. | Multiple inputs consuming prior outputs; multiple outputs creating new UTXOs. |
| **Token Mechanics** | Tokens exist as balance balances inside a specific contract (e.g., USDT `0xdAC17F...`). Transfers trigger contract code and emit `Transfer` logs. | Native assets only, or protocol overlays (Omni Layer); tokens do not share native transfer pipelines. |
| **Change Address Handling** | Absent. Senders transfer the exact required amount; leftover balance remains natively in the sender's account. | Essential. Transactions must spend whole UTXOs; the unspent difference is returned to a freshly generated change address. |
| **Graph Modeling** | Simple directed edges: $A \xrightarrow{\text{amount}} B$. Very clean 1-to-1 or 1-to-$N$ mapping. | Hypergraph or decomposed bipartite graph: $\text{Inputs} \{I_1, I_2\} \to \text{Tx} \to \text{Outputs} \{O_1, O_2\}$. |
| **Clustering Heuristics** | Gas parent funding correlation, contract deployment lineage, sweeper bot timing correlation. | Common Input Ownership Heuristic (CIOH), Change Address Identification (peeling chain heuristics). |
| **SIH Implementation Priority** | **Primary (95% of prototype scope):** Captures over 90% of active retail fraud cases reported to cyber cells. | **Secondary / Reference Model:** Requires complex UTXO unrolling and change detection heuristics. |

### 4.1 Step-by-Step Algorithmic Workflow

1. **Step 1: Input Validation & Network Classification:** Validate address format using checksum checks (EIP-55 for EVM, Base58Check for TRON). Verify the active token contract address (e.g., `TR7NHqjeKQxGTCi8q8ZY4pL8otSzgjLj6t` for TRON USDT).
2. **Step 2: Dual-Stream Data Acquisition:**
   - Query normal transactions (`txlist`) for gas fee context.
   - Query smart contract token transfers (`tokentx` or `/trc20`) for actual asset flows.
   - Query internal transactions (`txlistinternal`) to unmask contract-mediated forwarding.
3. **Step 3: Ingestion Normalization:** Transform heterogenous API payloads into a standardized `NormalizedTransaction` data object.
4. **Step 4: Constraint Pruning:** Apply temporal, value-taint, and fan-out limits to suppress spam transactions before graph construction.
5. **Step 5: Bounded Breadth-First Search (BFS):** Traverse outgoing edges level-by-level up to $k = 4$, logging every intermediate vertex, edge weight, and transaction hash into an adjacency list.
6. **Step 6: Trace Serialization:** Output the traversed sub-graph into a standardized JSON schema consumable by the visualization front-end and statutory dossier generator.

## 5. Mathematical Formulation & Taint-Tracking Models

When a suspect address mixes stolen funds with other balances and splits them across multiple outgoing transactions, a tracing engine must determine how much "taint" (illicit association) attaches to each branch.

```
       [Clean Funds: 2,000 USDT]    [Victim Stolen Funds: 8,000 USDT]
                              \      /
                               ▼    ▼
                       [Suspect Wallet V_0]
                       (Total: 10,000 USDT)
                                │
               ┌────────────────┴────────────────┐
               ▼ (Sends 7,000 USDT)              ▼ (Sends 3,000 USDT)
           [Wallet A]                        [Wallet B]
```

### Evaluation of Taint Accounting Models

1. **Poison Model (Universal Taint):**
   - *Logic:* If an address receives any tainted funds, all subsequent outgoing funds are considered 100% tainted until the balance reaches zero.
   - *Mathematical Form:* $\text{Taint}(e) = \text{True} \iff \text{Balance}(u) \cap \text{Illicit} > 0$.
   - *Forensic Critique:* **Produces extreme false positives.** In high-velocity wallets or OTC broker nodes, this model poisons the entire downstream ecosystem, making it legally indefensible in court.
2. **First-In, First-Out (FIFO) Model:**
   - *Logic:* Assumes funds spent first correspond to funds received first chronologically.
   - *Mathematical Form:* Outgoing transfers are matched sequentially against the queue of incoming UTXOs/deposits by block timestamp.
   - *Forensic Critique:* Vulnerable to deliberate anti-forensic maneuvering. Fraudsters can intentionally deposit clean funds immediately before spending, thereby claiming the outgoing transfer consisted only of clean assets.
3. **Proportional Haircut Model (Recommended for Prototype):**
   - *Logic:* Every outgoing transaction inherits a taint fraction strictly proportional to the ratio of illicit funds to total available balance at the time of transfer.
   - *Mathematical Formulation:*
     $$\text{Taint Ratio } R(u) = \frac{\sum V_{\text{illicit\_in}}(u)}{\text{Total Balance}(u)}$$
     $$\text{Tainted Value}(u \to v) = \text{Amount}(u \to v) \times R(u)$$
   - *Forensic Justification:* Mathematically objective, auditable, and transparent. It allows investigators to demonstrate to prosecutors exactly what percentage of the victim's funds reached an exchange deposit address.

## 6. Graph Construction, Path Constraints & Pruning Strategy

### 6.1 Directed Graph Mathematical Model
The investigation state is formalized as a Directed Multigraph $G = (V, E)$, where:
- $V$: Set of all unique blockchain addresses identified during the crawl.
- $E$: Set of directed edges $e = (u, v, k)$ where $u, v \in V$, representing discrete transfers from $u$ to $v$.
- $\omega(e)$: Property tuple containing:
  $$\omega(e) = \langle \text{tx\_hash}, \text{block\_number}, \text{timestamp}, \text{token\_symbol}, \text{value}, \text{taint\_value}, \text{tx\_fee} \rangle$$

### 6.2 State-Space Complexity & Pruning Rules
Without constraints, graph expansion exhibits exponential worst-case complexity:
$$\mathcal{O}\left(b^d\right)$$
where $b$ is the average branching factor (outgoing degree) and $d$ is the hop depth. If an address interacts with a DEX router or distribution contract with $b = 100$, depth $d = 4$ generates $10^8$ nodes, crashing the browser canvas and exhausting API rate limits.

To guarantee real-time performance ($\le 10$ seconds), the tracing engine applies three deterministic pruning rules:

```
┌────────────────────────┬───────────────────────────────────────────┬───────────────────────────────────────────┐
│ Constraint Rule        │ Mathematical Condition                    │ Technical Rationale                       │
├────────────────────────┼───────────────────────────────────────────┼───────────────────────────────────────────┤
│ 1. Temporal Filter     │ $t_{\text{tx}} \ge t_{\text{incident}}$   │ Discards all historical transactions that │
│                        │                                           │ occurred before the scam took place.      │
├────────────────────────┼───────────────────────────────────────────┼───────────────────────────────────────────┤
│ 2. Value-Taint Cutoff  │ $\text{Value}(e) \ge \max(\tau_{\min},    │ Filters dusting attacks, scam airdrops,   │
│                        │ \alpha \cdot V_{\text{victim}})$          │ and microscopic change transfers.         │
│                        │ (Default: $\$50$ or $5\%$ of loss)        │                                           │
├────────────────────────┼───────────────────────────────────────────┼───────────────────────────────────────────┤
│ 3. Branching Limit     │ OutDegree $(u) \le N_{\max}$              │ If a wallet splits funds to 50 addresses, │
│                        │ (Default: Top-5 by value)                 │ prioritize the top-5 value paths only.    │
├────────────────────────┼───────────────────────────────────────────┼───────────────────────────────────────────┤
│ 4. Cycle & Loop Trap   │ Visited $(v) == \text{True} \implies$ Terminate│ Breaks circular laundering loops without  │
│                        │ branch                                    │ causing infinite search recursion.        │
└────────────────────────┴───────────────────────────────────────────┴───────────────────────────────────────────┘
```

### 6.3 Algorithmic Traversal Choice: BFS vs. DFS
- **Why Breadth-First Search (BFS) is Mandatory:**
  - BFS discovers shortest paths first. If a scammer deposits into an exchange at Hop 2, BFS identifies it immediately without wasting compute exploring deep Hop 4 dead-ends.
  - BFS processes transactions level-by-level, enabling synchronous value-taint pruning across parallel branches at each hop.
  - DFS risks falling down infinite cycles or exploring irrelevant deep branches before ever inspecting immediate cash-out paths.

## 8. Concrete Technical Boundaries (What is Infeasible / Impossible)

Maintaining credibility in front of Ministry of Home Affairs evaluators requires clear articulation of blockchain investigation limits:

1. **No Direct Identity on Public Ledgers:**
   - Tracing maps value movements between public keys; it **never** proves who was sitting at the computer keyboard.
   - The trace establishes grounds for a legal freeze against a custodial entity; it does not replace off-chain police investigation.
2. **Zero-Knowledge Privacy Pools (Mixers) Break Direct Deterministic Trails:**
   - Protocols like Tornado Cash utilize zk-SNARK cryptographic proofs to sever the on-chain link between deposit commitments and withdrawal nullifiers.
   - When a trace hits a mixer contract, deterministic forward tracing must terminate. The system must flag: `"Funds entered Tornado Cash 100 ETH Pool at Hop 2"`, record the transaction hash, and highlight the obfuscation event in the case summary.
3. **Cross-Chain Bridge Opacity:**
   - When a suspect swaps EVM USDT for Bitcoin via a decentralized cross-chain protocol (e.g., THORChain), the EVM trace terminates at the router contract. Linking the corresponding Bitcoin payout requires off-chain bridge watcher monitoring or swap event indexers. For the prototype, cross-chain events are logged as terminal bridge interactions.
4. **Counterparty Interaction Does Not Equal Criminal Complicity:**
   - If funds flow into a decentralized exchange (e.g., Uniswap pool) or merchant processor, those protocols are automated code, not co-conspirators.
   - The system distinguishes between custodial VASP endpoints (where funds can be frozen) and non-custodial liquidity protocols.

## 11. Strategic Technical Answers to Evaluator Questions

### Q1: Given a victim-reported wallet address, what is the immediate first technical step?
**Answer:** Validate the address checksum and identify the blockchain network. Immediately ingest token transfer events (`tokentx` / TRC-20 logs) starting strictly from the victim's transfer timestamp $t_{\text{incident}}$. Do not perform full historical scraping; prioritize forward movements of the stolen asset type.

### Q2: Why does standard Ethereum RPC (`eth_getTransactionByHash`) fail to capture stablecoin fraud?
**Answer:** Native transactions only record ETH transfers. Stablecoins like USDT and USDC are ERC-20 smart contracts. Their movements occur within the contract's data payload and are emitted as on-chain event logs (`Transfer`). Tracing stablecoins requires querying event log topics or explorer-indexed token transfer endpoints.

### Q3: How does the system prevent the graph from exploding into tens of thousands of irrelevant nodes?
**Answer:** Through three mathematical pruning filters:
1. *Depth Bound:* Hard stop at $k = 4$ hops.
2. *Temporal Barrier:* Discarding transactions timestamped prior to the incident.
3. *Taint-Value Threshold:* Eliminating any branch transferring $< \$50$ USD or $< 5\%$ of the stolen amount, combined with a fan-out cap limiting evaluation to the top-5 highest value recipients per node.

### Q4: How is a circular laundering loop handled during traversal?
**Answer:** The traversal algorithm maintains a persistent hash-set of all visited addresses within the active case session. If an edge leads to an address already present in the visited set, the edge is recorded to complete the graph structure, but the engine halts further expansion along that branch, preventing infinite recursion.

### Q5: What is the technical difference between tracing and attribution?
**Answer:** Tracing (Role 2) is strictly deterministic and on-chain: it documents that address $A$ transferred $X$ tokens to address $B$ via transaction hash $H$. Attribution (Role 3) is inferential: it correlates address $B$'s subsequent behavior (e.g., an automated sweep to a known Binance hot wallet) with off-chain registries to assert that address $B$ is a Binance deposit account.
